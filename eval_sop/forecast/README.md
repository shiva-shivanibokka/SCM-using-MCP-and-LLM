# Forecasting evaluation: rolling-origin, multi-step backtest

Everything here is **measured** on the repo's **synthetic** dataset. Nothing is extrapolated. Raw outputs are in `results/`.

## Reproduce
```bash
# from repo root; DATABASE_URL must be empty so nothing is written to Postgres
DATABASE_URL= python eval_sop/forecast/backtest.py                 # main backtest (~70 min on a shared 24-core box)
DATABASE_URL= python eval_sop/forecast/leak_check.py               # before/after of the eval_set leak fix (~4 min)
DATABASE_URL= python eval_sop/forecast/repro/repro_eval_set_leak.py  # fast leak repro (stub model, ~20 s)
```
- Data: `data/huft_daily_demand.csv`, SHA256 `04d0834d90c3de1aaeae960d5b4b1a392714baa094fad49ec4d5d073cfa8e16c`. 175,360 rows: 160 SKUs × 1,096 days (2023-01-01 to 2025-12-31). The file is generated by `data/generate_data.py` and is gitignored.
- Versions: Python 3.12.3, catboost 1.2.10, pandas 3.0.2, numpy 2.5.0, Windows 11.
- Seeds: CatBoost `random_seed` ∈ {0, 1, 2}. Bootstrap seed 20251231 (2000 reps). The SKU-sampling seed (7) is unused because all SKUs were evaluated.
- Measured runtime of the main backtest: 4,186 s (about 70 min), with an LLM running concurrently on the same machine.

## Protocol
- **Origins** (last training day): 2025-06-30, 2025-08-31, 2025-10-31, 2025-12-01. **Horizon** H = 30 days, so each test window is o+1 to o+30, and the last one ends 2025-12-31.
- **Real multi-step forecasts.** No demand observed after the origin is used for any forecast. Recursive models feed their own predictions back as lags. Known-future features (calendar, promotion calendar) are allowed.
- **SKUs:** all 160 (640 SKU-origin pairs per model).
- **Syntetos-Boylan classification** on each training window (ADI > 1.32 means intermittent/lumpy; CV² cut-off 0.49). **Result: 0 intermittent SKUs at every origin; all 160 are "smooth".** The data contains no zero-demand days at all (max ADI = 1.0, max CV² = 0.19). The "intermittent" rows in `summary.csv` therefore have n = 0. **On this dataset, Croston/TSB routing is never exercised, and no claim about intermittent demand can be supported.**
- **Models**
  - `catboost_global`: the repo's `forecasting/ml_forecast.py` feature design. The 25 features in `_CB_FEATURES` are built with the repo's own `_make_cb_features` and `_build_promo_features`, with the repo's sorted SKU/category encoders. One global `Quantile:alpha=0.5` (p50) model is trained per origin, using the repo hyper-parameters (500 it, lr 0.04, depth 7, ...) except `thread_count=6`. Early stopping uses an **inner** split (the last 30 days of the training window). The forecast is recursive, and lag/rolling features are recomputed exactly as in training: `roll_mean_w` is the mean of the last w values, and `roll_std` uses ddof=1. In practice the best iteration was 491-499, so early stopping barely fires.
  - `catboost_repo_infer`: the same fitted model, but the forecast is made by the repo's served function `ml_forecast._forecast_catboost`, unmodified. That function has a train/serve skew. `_roll_mean`/`_roll_std` use the window `h[-(n+1):-1]`, which is shifted one day earlier than in training, and `np.std` uses ddof=0. Measured effect: none worth noting (13.22 vs 13.24 sMAPE).
  - `catboost_backend`: the design in `backend/forecasting/catboost_model.py`, which is what the ensemble and the README's `backtest_smape` (from `training.py::_backtest_one`) use. It is a per-SKU model on lags (1, 2, 3, 7, 14, 28) with 200 it, depth 4, lr 0.1, and a recursive forecast clipped at 0. The only change is an explicit `random_seed`.
  - Baselines: `naive` (last value), `snaive7` (last 7 days repeated), `ma28` (28-day mean), `croston` (α = 0.1; z₀ = first size, x₀ = first interval), and `tsb` (α = β = 0.1; z₀ = mean size, p₀ = demand frequency). Because there are no zeros, Croston and TSB both reduce to SES(0.1) and give identical numbers.
  - Not evaluated: Chronos, N-HiTS, TFT, and the blended ensemble (0.5/0.35/0.15). Their heavy dependencies are not installed, so the ensemble's accuracy remains unmeasured.
- **Metrics** (per SKU × origin):
  - sMAPE = 100/H · Σ 2|f−a|/(|a|+|f|), where a term with a = f = 0 counts as 0. (`training.py::_smape` instead drops 0/0 terms; this makes no difference here because there are no zeros.)
  - MASE₇ = MAE / mean|y_t − y_{t−7}| over the full training window. MASE₁ uses lag 1.
  - MAE.
- **Aggregation:**
  - Mean ± SD and median over the 640 pairs.
  - 95% CI from a **SKU-cluster bootstrap**: 160 SKUs resampled with replacement, all origins of a sampled SKU kept together, 2000 reps.
  - CatBoost "[seedmean]" means the metric is averaged over the 3 seeds within each pair. Per-seed rows are also reported.
  - Paired comparison: CatBoost minus the best baseline (chosen by mean on the test pairs, which favours the baseline), with a bootstrap CI of the mean difference and the win rate (ties count ½).

MASE₁ and MAE are in `results/summary.csv`. **Intermittent subset: n = 0 (no intermittent SKUs exist).**

**Paired comparison against MA28** (negative means CatBoost is better):
- `catboost_global`: ΔsMAPE = −1.53 pp, 95% CI [−1.92, −1.10]; median Δ −0.50; win rate 61.9%. ΔMASE₇ = −0.128 [−0.153, −0.102]; win rate 62.0%.
- `catboost_backend` (the model behind the README's backtest number): ΔsMAPE = **+3.03** pp, 95% CI [+2.73, +3.34]; win rate 23.4%. **It is worse than a 28-day moving average.**

**The advantage comes almost entirely from one origin.** Mean sMAPE by origin:

| origin | ma28 | catboost_global | catboost_backend | croston |
|---|---|---|---|---|
| 2025-06-30 | 12.71 | 13.12 | 13.16 | 13.02 |
| 2025-08-31 | 12.15 | 12.70 | 12.90 | 12.39 |
| 2025-10-31 (Nov, Diwali peak) | 19.72 | **13.07** | 23.99 | 24.02 |
| 2025-12-01 (Dec, year-end peak) | 14.51 | 14.06 | 21.14 | 15.17 |

CatBoost's win rate against MA28 is 44% and 40% at the first two origins, where MA28 is slightly better, then 94% (Nov) and 70% (Dec). CatBoost's edge comes from its calendar features (day-of-year, festival flags) capturing the synthetic Diwali and New-Year bumps, which a flat MA cannot anticipate. With only 4 origins, the SKU-bootstrap CI **does not capture origin-to-origin variance** and is therefore too narrow for a "general" claim.

**Seed variation** (mean sMAPE over 640 pairs):
- catboost_global: 13.27 / 13.35 / 13.10 (SD 0.13, range 0.25)
- repo_infer: 13.24 / 13.33 / 13.08
- backend: 17.68 / 17.80 / 17.92 (SD 0.12)

Seed variation is small compared with the gap to the baselines.

## How these numbers relate to the repo's claims
- `forecasting/ml_forecast.py:1166` (pre-fix) early-stopped on `X_va` and reported MAPE on that same `X_va` (lines 1171-1172). This is **confirmed** and now fixed; see `LEAK_FIX_NOTES.md` and `repro/`. Measured optimism: about 0.01 pp (11.96% vs 11.97% MAPE), negligible because early stopping hits the iteration cap. That number is a **one-step-ahead, true-lag** MAPE, not 30-day accuracy.
- The ensemble weights are hard-coded: `backend/forecasting/ensemble.py:16`, `ENSEMBLE_WEIGHTS = (0.5, 0.35, 0.15)`. The per-model "backtest_mape" values 12.4/14.1/16.8 are hard-coded defaults in `backend/forecasting/registry.py:31-33`. **Both confirmed; neither is backed by a run in this repo.**
- The registry backtest (`backend/forecasting/training.py:47-62, 65-83`) **is** recursive multi-step and is correctly called sMAPE. However, it covers only CatBoost, only the top-8 SKUs by volume (`_top_skus`), one fold, and no baseline. This is **confirmed**. The README's example `backtest_smape: 18.2` is consistent with our `catboost_backend` 17.8 on all SKUs, which is worse than MA28 (14.8).

## What the synthetic data allows you to conclude (`data/generate_data.py:2101-2160`)
Demand = `base_demand × indian_seasonality(day-of-year, year) × N(1, 0.12)`.
- The seasonality consists of smooth Gaussian bumps: Diwali +45% around day 300, New Year +25%, plus category-specific summer/monsoon/winter terms.
- There is a deterministic +35%/yr linear trend.
- There are about 24 random multiplicative spikes per SKU (×1.8-3.5) at uniformly random days, unrelated to the promotions file.
- Cold-chain SKUs get an extra N(1, 0.20) factor.

**There is no day-of-week effect, no zero demand, and no intermittency.** The promotions in `huft_promotions.csv` end in 2024, so the promo features are all zero across the test windows. Noise is i.i.d., so the best achievable accuracy is bounded by about 12% multiplicative noise plus unpredictable spikes. Because the data generator's seasonal shape matches the model's calendar features, the results show that CatBoost recovers a known synthetic seasonal curve. They are **not evidence of real-world retail forecasting accuracy**.

## Threats to validity
- Synthetic data, as described above. There are only 4 origins, and the result depends on whether a festival peak falls inside the window.
- The best baseline was picked on the test set, which favours the baseline.
- Hyper-parameters were not tuned. The 500-iteration cap is binding, since the best iteration is about 498.
- The ensemble, Chronos, N-HiTS, and TFT are untested.
- The inner early-stopping split is itself evaluated one step ahead.
